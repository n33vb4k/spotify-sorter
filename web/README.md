# spotify-sorter web app

Next.js app that sorts your Spotify Liked Songs into new private playlists by **listening** to them.
All audio analysis happens in the browser; the only server code is a stateless proxy for Deezer search.

## How it works

1. **Connect:** PKCE login with *your own* Spotify Client ID (no secret, nothing stored server-side).
2. **Scan:** reads Liked Songs 50 at a time.
3. **Listen:** for each song, `/api/preview` finds its 30-second Deezer preview; the browser downloads and
   decodes it to 16 kHz mono, and a Web Worker runs Essentia's Discogs-EffNet + mood models with
   `onnxruntime-web`. Tags are cached in IndexedDB, so a run can stop and resume.
4. **Review:** songs are grouped by top style (`src/lib/grouping.ts`); rename, move or leave songs out.
5. **Create:** new private playlists only. Existing playlists are never edited; name clashes are skipped.

Optional **Skips**: load Spotify's *Extended streaming history* export to find liked songs you always
skip. Files are parsed locally and never uploaded.

The browser pipeline matches Essentia's own Python/TensorFlow pipeline: 12/12 top styles identical on real
previews (`/dev/parity` in development), and the mel features are unit-tested to within 1e-4 against a
fixture generated by `ml/make_fixture.py`.

## Develop

```sh
npm install
npm run models        # downloads the Essentia ONNX models into public/models (retries; the server is slow)
npm run dev           # then open http://127.0.0.1:3000 (Spotify rejects "localhost" redirect URIs)
npm test              # mel/grouping/skips tests; the full-model test runs if ../ml/models exists
```

To try it with your account, create an app at <https://developer.spotify.com/dashboard> with redirect URI
`http://127.0.0.1:3000/callback` and paste its Client ID into the Connect step.

## Deploy (Vercel, free tier)

1. Import the repo in Vercel and set **Root Directory** to `web`. `vercel.json` sets the build command to
   `npm run models && npm run build`.
2. **Environment variables** (see `.env.example`), both optional:
   - `NEXT_PUBLIC_SPOTIFY_CLIENT_ID`: your Spotify app's Client ID. People you've added under **User
     Management** in that app's dashboard connect in one click; anyone else can still bring their own Client
     ID (the app detects Spotify's "user not registered" response and offers that route).
   - `NEXT_PUBLIC_MODEL_BASE`: load models from elsewhere (e.g. a GitHub Release) if Essentia's server is
     flaky during builds. Unmodified redistribution with attribution is allowed by the models' licence.
3. In your Spotify app, add `https://<your-domain>/callback` as a redirect URI. Friends using their own app
   add the same URI to theirs.
4. Recommended: in Vercel → Firewall, add a rate-limit rule on `/api/preview` (e.g. 600 requests/min per IP).
   The route already limits each instance to 300/min per IP, which a real tagging run (about 60–120/min)
   never reaches; the firewall rule covers traffic spread across instances.

### Security

- No server-side secrets or storage. Login is PKCE in the browser; tokens live in the visitor's browser.
- Strict security headers (`next.config.ts`): CSP limited to this site, Spotify's API and Deezer's preview
  CDN; no framing; no referrer from `/callback`; HSTS. The CSP allows inline scripts because the pages are
  statically rendered (nonces would force dynamic rendering); the app never renders user data as HTML.
- `/api/preview` only calls Deezer's fixed API host, rejects cross-site requests, caps input length, and is
  rate-limited; clients back off and retry on 429, so normal use isn't slowed.
- `/dev/parity` returns 404 in production unless built with `ENABLE_DEV_PAGES=1`.

## Limits

- Spotify development-mode apps only work for accounts added in that app's dashboard, which is why each
  person brings their own Client ID.
- Some songs have no Deezer preview; they're left out of the plan and shown as untagged.
- Styles are the model's best guess. The UI shows confidence and lets you move anything.
